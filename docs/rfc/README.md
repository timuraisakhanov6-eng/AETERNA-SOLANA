# Request For Comments (RFC)

Version: 1.0

Status: Informational

---

# Purpose

This directory contains Requests for Comments (RFCs).

RFC documents describe proposed protocol, architecture, engineering, or implementation changes that are under discussion.

RFC documents are discussion documents.

They are not part of the canonical documentation unless explicitly adopted.

---

# Authority

RFC documents have lower authority than canonical documentation.

RFC documents must never:

- redefine protocol behavior;
- override canonical documentation;
- justify implementation changes;
- be treated as the source of truth.

Canonical documentation always takes precedence.

---

# Lifecycle

An RFC may be:

- proposed;
- reviewed;
- accepted;
- rejected;
- superseded.

Only accepted RFCs may be incorporated into the canonical documentation.

Acceptance alone does not make an RFC canonical.

A proposal becomes canonical only after its contents have been incorporated into the appropriate canonical document.

# Relationship to Canonical Documentation

RFC documents are engineering proposals.

Canonical documentation defines the protocol.

Whenever an RFC conflicts with canonical documentation:

The canonical documentation prevails.

---

# Relationship to AI Documentation

AI systems may review RFC documents when explicitly requested.

RFC documents must never be treated as governing documentation during implementation or review unless their contents have been incorporated into the canonical documentation.

---

# Final Principle

RFC documents exist to discuss possible future changes.

They never modify the protocol directly.

The protocol changes only through approved updates to the canonical documentation.
