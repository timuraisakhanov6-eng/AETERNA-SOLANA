# AETERNA Project Intake

Version: 1.0
Status: Canonical

---

# Purpose

This document defines the mandatory onboarding process for every Artificial Intelligence system before performing any work on the AETERNA project.

No implementation, analysis, review, or recommendation may begin until this process has been completed.

---

# Rule 1 — Read Before Acting

The AI must never begin working immediately.

The AI must first study the project.

Understanding always precedes implementation.

---

# Rule 2 — Mandatory Reading Order

The AI must read the following documents in this exact order.

1. AI Constitution
2. AETERNA Complete Engineering Model
3. AETERNA Complete Project Logic
4. AETERNA Complete System Logic
5. Applicable Canonical Specifications
6. Additional project documentation
7. Current implementation

This order is mandatory.

It must never be changed.

---

# Rule 3 — Understanding Before Modification

Before modifying any implementation, the AI must understand:

- the protocol;
- the architecture;
- the authority model;
- the implementation boundaries;
- the protocol invariants.

The AI must never modify code it does not understand.

---

# Rule 4 — Documentation Before Source Code

Documentation defines the protocol.

Source code implements the protocol.

Documentation must always be studied before source code.

---

# Rule 5 — Source Code Is Evidence

The current implementation is an implementation reference.

It is not automatically the protocol.

Source code must always be interpreted in the context of canonical documentation.

If code and documentation disagree, the conflict must be reported.

The AI must never assume that code is correct solely because it exists.

---

# Rule 6 — Working With Existing Implementation

The AI must identify whether the requested work is:

- implementation;
- bug fixing;
- refactoring;
- documentation;
- review;
- protocol analysis.

The AI must never perform architectural redesign when the requested work concerns implementation.

---

# Rule 7 — Conflict Resolution

If a conflict is discovered:

1. Identify every conflicting source.
2. Determine the highest-authority source.
3. Explain the conflict.
4. Recommend the minimum implementation change required to restore consistency.
5. Wait for approval before changing canonical documentation.

---

# Rule 8 — Missing Information

If required information is unavailable:

The AI must stop.

The AI must explain exactly which information is missing.

The AI must request clarification.

The AI must never invent protocol behavior.

---

# Rule 9 — ZIP Repository

The repository represents the current implementation of the protocol.

It is a reference implementation.

It is not automatically the canonical definition of the protocol.

The repository must always be interpreted together with the canonical documentation.

---

# Rule 10 — Ready State

The AI may begin implementation only after:

- reading all required documentation;
- understanding the architecture;
- identifying the applicable protocol rules;
- confirming that sufficient information exists to perform the requested task.

If any of these conditions is not satisfied, implementation must not begin.
